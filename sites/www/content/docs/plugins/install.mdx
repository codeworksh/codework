Every plugin command lives under `codework plugin`. They read and write the same settings files CodeWork loads from, so what you see in `codework plugin list` is what your next session gets.

## Add a plugin

`plugin add` installs a plugin, checks that it really is a plugin, and then writes it into a settings file:

```bash
codework plugin add @acme/codework-tool-proc
```

```text
Added acme.tool.proc (@acme/codework-tool-proc@1.2.0) to /work/app/.codework/settings.jsonc
```

By default the entry goes into your project's `.codework/settings.jsonc`. CodeWork finds it by searching up from the current directory. If no parent directory has a `.codework/` directory, CodeWork creates one in the current directory and prints `Created <path>/`, so a mistyped `cd` is easy to spot.

| Flag             | What it does                                                                                    |
| ---------------- | ----------------------------------------------------------------------------------------------- |
| `-g`, `--global` | Write your user settings (`~/.codework/settings.jsonc`) so the plugin applies to every project. |
| `--session <id>` | Write the project a session is linked to (see `codework session link`), from any directory.     |

`plugin add` validates before it writes. If the spec does not resolve, the download fails, or the module does not export a plugin, you get that error and your settings file is left untouched.

`plugin add` rewrites only the `plugins` array, so comments and formatting elsewhere in the file are kept. Adding a plugin that is already there, under another version or spelling, replaces its entry instead of adding a second one.

The entry is written the way you typed it. `@acme/codework-tool-proc` with no version follows `latest`. To pin a plugin, add it with an exact version or a full commit SHA. That entry is the pin: there is no lockfile.

### Supported sources

```bash
# npm: exact version, range, or tag
codework plugin add @acme/codework-tool-proc@1.2.0
codework plugin add @acme/codework-tool-proc@^1
codework plugin add @acme/codework-tool-proc        # same as @latest

# git: branch, tag, or full commit SHA
codework plugin add github:acme/codework-tool-proc#v1.2.0
codework plugin add "git+https://github.com/acme/tools.git#main::path:packages/proc"

# local: a file, a package directory, or a file:/// URL
codework plugin add ./plugins/house-style.ts
```

A relative path is resolved from where you run the command (or from the linked session's directory with `--session`). When the plugin and the settings file are both inside the project, the entry is written relative to the settings file so it works in any checkout. Otherwise, as with `-g`, an absolute path is written. Remote tarball URLs are not supported.

Private registries work through your normal `.npmrc`. CodeWork reads the `.npmrc` chain from the project that declares the plugin, so a scoped registry and token configured in the repository are the ones used to install it.

## Install what settings already name

When you clone a repository whose `.codework/settings.jsonc` already lists plugins, fetch them all at once:

```bash
codework plugin install
```

```text
Installed @acme/codework-tool-proc@1.2.0 (acme.tool.proc)
1 installed, 2 already present, 1 local
```

This is the plugin equivalent of `pnpm install` with no arguments. It writes nothing to settings, skips anything already in the store, and skips local paths, which are loaded where they are.

## Resolve-only loading

CodeWork never installs a plugin while it is running a session. At startup, and at every turn after that, it only looks in the local store and imports what is there.

This means:

- **Offline starts work.** Once plugins are installed, nothing about running a session depends on a registry being reachable.
- **Missing plugins are reported, not fetched.** A plugin from your user settings that is not installed stops startup with `plugin-not-installed`. One from a project's settings is left out of the session with a warning that it is configured but not loaded. Both tell you to run `codework plugin install`.
- **Updates are opt-in.** A range like `^1` does not drift on its own. Newer versions arrive only when you run `plugin install`, `plugin update`, or `plugin add`.
- **Installs land without a restart.** A running server notices a newly installed or updated plugin at the next turn and loads it. Turns already in progress keep the version they started with.

`plugin list` and `plugin remove` never install anything either.

<Callout title="Why not install on demand?">
	Installing at startup turns every fresh start into a possible network wait, fails offline, and lets registry timing
	decide which code runs. Keeping installs explicit means the same settings always load the same bytes.
</Callout>

## List configured plugins

```bash
codework plugin list
```

```text
@acme/codework-tool-proc@1.2.0  acme.tool.proc
./plugins/house-style.ts        local.prompt.house-style
github:acme/broken#main         plugin-not-installed
```

The left column is each module entry exactly as your settings spell it. The right column is the plugin ID it resolved to. A plugin ID there means every step worked: the entry parsed, the store had it, and the module imported and validated. When something fails, the [error slug](/docs/plugins/troubleshooting) appears in its place. Built-in plugins and configuration entries are not listed.

Add `--verbose` to see the full message behind a failure and which settings file declared each entry.

## Check for and apply updates

`plugin check` asks the registry or git remote which plugins have a newer revision. Entries pinned to an exact version or commit have nothing to check, and local plugins are skipped.

```bash
codework plugin check
codework plugin check @acme/codework-tool-proc   # one plugin
codework plugin check --refresh                  # ignore the cached answer
```

```text
@acme/codework-tool-proc@^1  1.2.0 -> 1.3.1
1 update available.
```

Answers are cached for an hour. Use `--refresh` right after you publish a new version of your own plugin. If a remote cannot be reached, `check` says so and exits non-zero rather than reporting you as up to date.

`plugin update` fetches a newer revision of every installed plugin that has one:

```bash
codework plugin update
codework plugin update @acme/codework-tool-proc
```

Both commands name a plugin by package, git spec, or path, not by plugin ID. `update` only refreshes plugins that are already installed; use `plugin install` for the rest. Updates install side by side with the version in use, so a session that is already running is never disturbed.

## Reload local plugins

When you are developing a local plugin against a running server (`codework serve`), pick up your edits without restarting:

```bash
codework plugin reload
codework plugin reload --server ws://127.0.0.1:7433/rpc/v1
```

You only need this for local files. Installed packages are picked up automatically at the next turn, and every `codework run` without `--server` starts a fresh process that loads everything anyway. If the reload fails, the server keeps the plugins it already had loaded.

## Remove a plugin

```bash
codework plugin remove @acme/codework-tool-proc
codework plugin remove acme.tool.proc -g
```

You can name the plugin by package, path, or plugin ID. An npm package matches with or without the version you added it with; a git spec must include its `#` ref. `remove` deletes the module entry and any configuration entries written for it. For a plugin that is broken or not installed, name it by package or path, since its ID can only be read from an installed copy.

## Command reference

| Command                         | What it does                                                |
| ------------------------------- | ----------------------------------------------------------- |
| `codework plugin add <spec>`    | Install a plugin and add it to a settings file.             |
| `codework plugin install`       | Install every plugin the settings files name.               |
| `codework plugin list`          | List configured plugins and what each one resolved to.      |
| `codework plugin check [spec]`  | Report which configured plugins have a newer revision.      |
| `codework plugin update [spec]` | Fetch a newer revision of every plugin that has one.        |
| `codework plugin reload`        | Re-import configured plugins in a running server.           |
| `codework plugin remove <spec>` | Remove a plugin and its configuration from a settings file. |

Every command also accepts the `--home` and `--user-config-dir` flags to point at a different CodeWork home or user settings directory.
